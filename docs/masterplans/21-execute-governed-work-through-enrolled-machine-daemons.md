# Execute governed work through enrolled machine daemons

This MasterPlan is a living document. The sections Progress, Surprises & Discoveries,
Decision Log, and Outcomes & Retrospective must be kept up to date as work proceeds.
If durable project context changes, update or create ADRs in docs/adr/ in the same change.


## Vision & Scope

Deliver [IR-20](../improvement-requests/execute-governed-work-through-machine-daemons.md). After this initiative a person who owns a machine (a developer laptop, a build box, a device host) runs one small process on it, `shikigami-machine`, and the central Shikigami runtime can run the workspace operations it already knows how to run on that machine instead of on its own host. The daemon connects outbound only, over TLS to a new central role `shikigami-machine-gateway`, authenticates with a key pair that never leaves the machine, and offers a closed set of typed workspace operations: provision a private repository copy at an approved commit, bounded read and list, structured file replacement, a supervised validation command, Git status, diff and commit, exact-artifact integration, fence and write admission for ownership transfer, and terminal cleanup. There is no shell. Enrollment is an explicit act on both sides: the central operator offers a one-time code and later approves the machine's key fingerprint, and the machine's operator runs the enrollment with that code and pins the gateway's certificate. Each identity is individually revocable, and a revoked machine is refused at its next connection and on every retry.

The machine is the enforcement point. Its operator writes a local policy file naming the repositories the machine will host and where their Git object stores live, the agent principals it accepts, the operation classes it allows, the containment profile it has qualified, and the resource ceilings it imposes. The daemon admits a command only when the central grant and the local policy both allow it, and nothing in a command can widen the local policy. Every command is bound to the machine's identity, the workspace, the assignment, the owner epoch, the logical operation and the actual attempt, so a captured command cannot run on another machine, under another owner, or twice. A compromised central runtime holding every central credential can therefore do no more on a machine than that machine's local policy already allowed for the repositories it already hosted.

The durable workflow, model calls, objective state, resource accounting and every PostgreSQL store stay in the central runtime exactly as today. The daemon holds no database credential, no model provider credential and no Kikan-En client; it holds its own key, its local policy, a ledger of fences it has applied, and the receipts of commands it has executed until the central runtime acknowledges them. Absence is a normal state: a disconnected machine leaves its commands queued and its executions unresolved, never failed; a command already admitted on the machine settles under its own absolute deadline and local cancellation without the central connection; a lost acknowledgement is unknown until the machine's retained receipt settles it exactly once on reconnection; and a timeout alone never counts as failure. Fencing holds across a partition: a transfer away from an unreachable machine starts the successor on an explicit approved base in a new workspace, the old machine receives the pending fence before anything else when it returns, its stale commands are refused, and its late results settle only the former attempt's accounting. The single-host deployment keeps working unchanged: a grant without a machine placement still uses the socket-activated supervisor from [plan 96](../plans/96-provide-governed-mutable-repository-workspaces-for-durable-agents.md).

Operators see enrolled machines, their connection state, platform and containment profile, policy revision, placed assignments, queued and unresolved commands and pending fences through `shikigami machines list|inspect --json` centrally and `shikigami-machine status --json` on the machine, and through exported metrics. Qualification runs on at least two disposable Apple containers behind a severable network, not on the host alone.

Out of scope, as the request states: native macOS containment (a machine without a qualified profile hosts edits and Git but refuses process tools), mobile or intermittently powered devices beyond the disconnected-state contract, a machine marketplace, model calls from the daemon, and interactive terminal attachment. Reading a person's uncommitted working tree is excluded by design: the only supported value of the working-tree grant in this delivery is refusal, and the daemon provisions every workspace from the Git object store at an approved commit. Integrating worker commits that live on different machines is excluded as well: the central host receives commit identities, never objects, so exact-artifact integration runs on a machine only when every worker workspace and the integration workspace share that machine, and artifact transport between machines is future work. [A2A interoperability](../improvement-requests/support-a2a-cross-runtime-agent-interoperability.md) connects independent runtimes and is unrelated; [plan 78](../plans/78-run-external-operations-from-durable-flows-through-idempotent-shiki-jobs.md)'s generic executor is not selected. A dedicated lightweight package for the daemon binary is a deliberate exclusion recorded in the Decision Log.


## Decomposition Strategy

Five children in three phases. Phase A is EP-1, the trust and transport slice: machine identity, enrollment and revocation, the central machine registry, the framed protocol with its closed operation and receipt vocabulary, the gateway role that accepts outbound sessions, and the daemon skeleton that enrolls, connects, authenticates and heartbeats but executes nothing. Phase B runs two independent lines against EP-1's types. The machine line is EP-2, local policy and command admission with the retained ledger, followed by EP-3, which hosts the physical workspace operations on the machine with local deadlines and retained receipts. The central line is EP-4, which places assignments on machines, relays bound commands durably, settles receipts through the existing execution owner, and defines absence and partition semantics. Phase C is EP-5, which makes machines observable to operators and qualifies all nine IR-20 acceptance cases together across severable Apple containers.

Trust and transport are separate from policy because they have different proofs and different failure modes. EP-1 is proven by enrollment, authentication, revocation and reconnection against the registry with the daemon executing nothing; its acceptance is about identities and sessions. EP-2 is proven in-process by feeding bound command frames to a pure admission function over a policy file and a fence ledger, with no network and no runtime; its acceptance is about refusals and convergence. Policy is separate from the physical host because the admission rule is pure Haskell that must be total and property-checkable, while EP-3 touches the C-backed contained file adapter, Git object store, systemd units and the output collector and can only be qualified inside a Linux guest. The central relay is its own child because it is the only one that edits the durable execution owner's integration (`Shikigami.Execution.Store` receipt paths, the protected admission snapshot, the workspace catalog and binding, and the worker composition root), and because its semantics for absence and partition are the request's central contract and deserve a PostgreSQL suite of their own against an in-process fake daemon before the real one exists. Observability and qualification are a separate child because the operator surface and metrics need real sessions and real commands, and because IR-20 closure must not be claimed before every acceptance case has evidence from at least two machines behind a severed network.

The decisive architectural choice is that the daemon is thin. The current `shikigami-workspace-supervisor` (`shikigami-workers/src/Shikigami/Workspace/Daemon.hs`) opens the central database, verifies migrations, builds the Kikan-En authorizer and the Meibo directory, and serves four requests (`RpcLaunch`, `RpcObserve`, `RpcFence`, `RpcAdmitWrite`) on a kernel-peer-checked Unix socket; its stores (`Workspace.Store`, `ProcessStore`, `GitStore`, `TransferStore`, `CleanupStore`, `ProcessProfileStore`) are PostgreSQL transactions. Running that process on a remote machine would hand every machine a central database credential, which is precisely what the request forbids. Rewriting those stores for a machine-local database would duplicate the durable bookkeeping and introduce a second owner of reservations and epochs. Instead the physical steps that are already separate modules (`ContainedFile`, `GitObjects`, `GitCapture`, `Systemd`, `Collector`, `Provision`, `Allocation`) are exposed behind one physical interface that both the existing supervisor and the new daemon call; the central runtime keeps every reservation, epoch, receipt row and attempt in PostgreSQL; and the daemon retains only its identity, its policy, the fences it has applied and the receipts not yet acknowledged, in fsynced files under its state directory. Receipts enter the central execution owner through the same independent late-receipt path the supervisor uses today (`publishProcessReceipt` in `shikigami-workers/src/Shikigami/Workspace/Supervisor.hs`, which calls `Execution.recordIndependentToolReceipt`), so [ADR 0060](../adr/0060-safe-recovery-spends-new-attempts-and-retains-independent-receipts.md)'s contract is reused rather than reinvented.

Alternatives considered. One ExecPlan was rejected: identity, policy, physical hosting, central relay and qualification cut across core, workers and server, add two roles and two migrations, and have independent proofs. One child per IR-20 acceptance item was rejected because the items share mechanisms (items 1, 4 and 6 all exercise relay and receipts; items 2, 3 and 8 all exercise local admission). A fat daemon that opens the central database was rejected for the credential reason above. Mutual TLS with X.509 client certificates was rejected in favor of a server-authenticated TLS session with the gateway certificate pinned at enrollment plus an Ed25519 challenge-response for the machine: the private key still never leaves the machine, each session is bound to a fresh server nonce, revocation is a registry check at hello, and no certificate authority or client-certificate plumbing is needed; Mori has `crypton` registered (`kazu-yamamoto/crypton`) and `warp-tls`, `wai-websockets` and `websockets` in `yesodweb/wai`, while no X.509 helper is registered. A raw framed TCP stream was rejected in favor of WebSocket over TLS through Warp because the gateway then shares the health routes, proxy and load-balancer behavior the server already has, and `websockets` is already a dependency of both core and workers. A machine-local SQLite ledger was rejected because no SQLite binding is registered in Mori and the file provider already proves fsynced receipt files with atomic publication. Moving an assignment between machines by copying the old workspace was rejected by the request: a move uses fenced handoff and an explicit base. An eighth Cabal package for a lightweight daemon binary was deferred: the physical modules live in `shikigami-workers`, the Nix cohort asserts seven application packages, and [ADR 0003](../adr/0003-a-seventh-package-keeps-one-off-agent-runs-light.md) makes a package split a recorded decision; the first delivery places `shikigami-machine` in `shikigami-workers`, requires that it start with no database, queue or Kafka configuration, and records the weight cost.

Research against `88926307` verified every module, symbol and ADR the children cite. The facts that shaped the decomposition: `Shikigami.Workspace.Protocol` already frames one JSON request per connection with `format` and `action` fields and refuses unknown keys; `Shikigami.Workspace.RpcClient.callRpc` checks kernel peer credentials and validates every reply against its request; `Shikigami.Workspace.ProcessProvider` is the existing `DurableAdapter` that launches through the socket, polls `RpcObserve`, and on timeout throws so the executor keeps the uncertain-effect reservation; `WorkspaceSettings` holds `repositories`, `grants` and an optional `process` block and refuses unknown fields; `WorkspaceBinding` carries `id :: WorkspaceId` (KindID `shikigami_workspace`), `request`, `workspace :: WorkspaceRef`, `repository`, `base`, `policyRevision`, `storageRoot` and `source`; `WorkspaceAdmission` carries the frozen `filePolicy`; `DispatchContext` carries `attemptId`, `owner :: ClaimOwner` and `generation :: StateRevision "execution-attempt"`; `Execution.Store` exposes `recordIndependentToolReceipt`, `recordLateExecutionReceipt`, `markExpiredExecutionAttemptUncertain` and `publishExecutionWake`; `Shikigami.App.Config.Role` is a closed sum with `roleRequiredKeys` and `roleBinary`; `Shikigami.Telemetry.Metrics.ShikigamiMetrics` names instruments `shikigami.<noun>.<verb>`; `tools/style/module-ownership.json` lists `Workspace` but no `Machine` root; the latest migration is `0042`, and MasterPlans 19 and 20 also plan migrations, so numbers are allocated at implementation time with `just new-migration`; Apple `container` 1.5.0 has `container network create|delete|inspect`; and `tests/workspace/run-apple.sh` builds `shikigami-workspace-prototype` through Nix, copies it into one guest and runs `run-linux.sh` there.

## Dependency Graph

```text
EP-1 (119) ---+---> EP-2 (120) ---> EP-3 (121) ---+
              |                        ^          +---> EP-5 (123)
              +---> EP-4 (122) --------+ (completion gate for EP-4 M3)
                        |
                        +-------------------------+

EP-2 and EP-4 proceed in parallel once EP-1 is Complete.
EP-3 follows EP-2 on the machine line; EP-4 M1-M2 run on the central line
against a fake daemon; EP-4 M3 needs the real daemon from EP-3.
```

EP-2 requires EP-1 because its admission function consumes EP-1's `CommandEnvelope`, `MachineOperation`, `OperationClass` and `MachineRefusal` types and because the ledger it retains is keyed by EP-1's `MachineCommandId`; defining those in EP-2 would force EP-4 to wait for the whole machine line. EP-3 requires EP-2 because every physical operation runs only after `admitCommand` has accepted the envelope, and because the receipts EP-3 produces are retained by EP-2's ledger until acknowledged. EP-4 requires EP-1 because it enqueues commands into EP-1's registry, delivers them through EP-1's gateway session and reads EP-1's refusal vocabulary when a machine refuses; it does not require EP-2 or EP-3 to begin, because its absence and settlement semantics are proven against an in-process fake daemon that speaks EP-1's protocol. EP-4's third milestone requires EP-3 because the partition cases (sever during a command, transfer during a partition, reconnect with a pending fence) need a daemon that really enforces a local deadline and really retains a receipt. EP-5 requires EP-3 and EP-4 because inspection reads what real sessions and real commands write, and the qualification harness drives real enrollment, real commands and real severance.

No child waits on any plan outside this MasterPlan. EP-1 may begin immediately. The one representative producer/consumer check scheduled before dependent variants expand is owned by EP-1 milestone 3: a daemon enrolled in one process authenticates to a gateway in another process over TLS, receives a `Welcome` carrying an empty fence list, heartbeats, is revoked, and is refused on reconnection, with the registry row showing each state. EP-2 and EP-4 both build on that session.


## Integration Points

**Machine vocabulary and protocol — EP-1 owns; EP-2, EP-3, EP-4 and EP-5 consume.** `shikigami-core/src/Shikigami/Machine/Types.hs` defines, following the house value rules: allocated identities `MachineId`, `EnrollmentOfferId`, `MachineSessionId` and `MachineCommandId` as private newtypes over `KindID` with the singular prefixes `shikigami_machine`, `shikigami_machine_enrollment`, `shikigami_machine_session` and `shikigami_machine_command`, minted as UUIDv7 only by the owning store or ledger and admitted through checked parsers (`parseMachineId :: Text -> Either Text MachineId`, `machineIdText`, `newMachineId :: IO MachineId`), with no `Generic`, `IsString` or coercion escape; the checked `MachineName` (1 to 64 lowercase letters, digits and hyphens, the operator-facing label); `KeyFingerprint` (lowercase hex SHA-256 of the raw Ed25519 public key) and `MachinePublicKey` (32 bytes, checked); `EnrollmentCode`, an opaque secret with no `Show` or JSON encoder beyond the one-time printer; the closed `MachineStatus` (`Offered | AwaitingApproval | Enrolled | Revoked`); the closed `Platform` (`LinuxPlatform | DarwinPlatform | OtherPlatform`) and `ContainmentProfile` (`SystemdCgroupV2 !(WorkspaceCoordinate "process-properties") | UnqualifiedPlatform`; the refusal constructor `UnqualifiedContainment` below is a different type, so the two names must stay distinct); `PolicyRevision` as `WorkspaceCoordinate "machine-policy"`; the closed `ConnectionState` (`NeverConnected | Connected {since, session} | Disconnected {since, lastSession}`); the closed `OperationClass` (`ProvisionClass | ReadClass | EditClass | ProcessClass | GitClass | IntegrationClass | OwnershipClass | CleanupClass`); and the closed `MachineRefusal` (`OutsidePolicy !OperationClass | WrongMachine | StaleEpoch | UnknownRepository | UnqualifiedContainment | CeilingExceeded !CeilingKind | MalformedCommand | MachineRevoked`). `shikigami-core/src/Shikigami/Machine/Protocol.hs` defines the frames (`Hello`, `Challenge`, `Proof`, `Welcome`, `Refused`, `Heartbeat`, `Command`, `Receipt`, `Ack`, `Fence`, `FenceApplied`), each JSON object carrying a `format` version and refusing unknown keys as `Workspace.Protocol` does; `CommandEnvelope {commandId, binding :: CommandBinding, operation :: MachineOperation, deadline :: UTCTime, issuedAt}` where `CommandBinding {machine :: MachineId, workspace :: WorkspaceRef, bindingDigest :: WorkspaceCoordinate "binding-digest", repository :: RepositoryId, base :: WorkspaceCoordinate "git-object", assignment :: AssignmentKey, owner :: AgentIdentity, epoch :: StateRevision "worker-owner", operationId, attemptId, claimOwner :: ClaimOwner, generation :: StateRevision "execution-attempt"}` (the repository and base travel in the binding so that every operation, not only `Provision`, can be checked against local policy); the closed `MachineOperation` sum (`Provision`, `ReadFile`, `ListFiles`, `ReplaceFile !Replacement`, `LaunchProcess`, `ObserveProcess`, `CancelProcess`, `GitStatus`, `GitDiff`, `GitCommit`, `Integrate`, `FenceOwner !TransferIntent`, `AdmitWrite`, `Cleanup`) with `operationClass :: MachineOperation -> OperationClass` total; and `ReceiptEnvelope {commandId, binding, outcome :: MachineOutcome}` where `MachineOutcome` is the closed sum of `Provisioned`, `FileRead`, `FilesListed`, `FileReplaced !FileReceipt`, `ProcessObserved !ProcessView`, `GitObserved`, `GitCommitted`, `Integrated`, `Fenced !FenceOutcome`, `WriteAdmitted`, `CleanedUp`, `Refused !MachineRefusal` and `Unresolved`. Payload types reuse `Shikigami.Workspace.Provider.Replacement` and `FileReceipt`, `Shikigami.Workspace.Protocol.ProcessView`, `Shikigami.Workspace.Process.ProcessReceipt`, `Shikigami.Workspace.GitTypes`, and `Shikigami.WorkerSession.Transfer.TransferIntent` and `FenceOutcome`; no child defines a second edit, process, Git or fence vocabulary. Bounded content fields (read bytes, diff bytes, stdout and stderr prefixes) keep the existing 1 MiB ceiling from `validView`. Later children add constructors only by recording the change here; EP-2 may not widen `MachineRefusal` without EP-4 agreeing, because EP-4 maps every refusal to a central command state.

**Machine registry — EP-1 owns the schema and store; EP-4 and EP-5 extend and read.** One migration, allocated with `just new-migration machine-registry` at implementation time, creates `shikigami.machines` (machine id, name, status, key fingerprint, public key, platform, containment profile, policy revision, enrolled and revoked timestamps), `shikigami.machine_enrollments` (offer id, name, hashed code, expiry, approving operator, resulting machine) and `shikigami.machine_sessions` (session id, machine, connected and disconnected timestamps, gateway instance). `shikigami-core/src/Shikigami/Machine/Store.hs` exposes `offerEnrollmentTx`, `claimEnrollmentTx`, `approveMachineTx`, `revokeMachineTx`, `recordSessionOpenedTx`, `recordSessionClosedTx`, `inspectMachineTx`, `inspectMachinePageTx` and the typed-row readers that refuse corruption inside the transaction as [ADR 0101](../adr/0101-process-intent-decoding-preserves-launch-and-receipt-uncertainty.md) requires. EP-4 adds `shikigami.machine_commands` and `shikigami.machine_fences` in its own migration and extends the store with `enqueueCommandTx`, `deliverableCommandsTx`, `markDeliveredTx`, `settleCommandTx`, `supersedeCommandsTx`, `recordPendingFenceTx` and `markFenceAppliedTx`. EP-5 adds bounded page readers. Every state change is a conditional transition on the current status, and revocation is a terminal status that no later transition reopens.

**Gateway role and daemon skeleton — EP-1 owns; EP-3 and EP-4 extend.** `shikigami-workers/src/Shikigami/Machine/Gateway.hs` serves the WebSocket endpoint over TLS through `warp-tls` and `wai-websockets`, performs the hello, challenge, proof and welcome exchange, binds the socket to the authenticated `MachineId`, enforces heartbeats and closes on revocation. `shikigami-workers/src/Shikigami/Machine/Client.hs` is the daemon's outbound session with bounded reconnection backoff, the pinned gateway fingerprint check (`crypton` SHA-256 over the DER certificate), Ed25519 signing (`crypton`), and a `MachineSessionHandler` record of callbacks (`onCommand`, `onFence`, `onAck`) that EP-3 fills. Two new roles join `Shikigami.App.Config.Role`: `MachineGatewayRole` (binary `shikigami-machine-gateway`, required keys database and `machine.gateway`) and `MachineDaemonRole` (binary `shikigami-machine`, required key `machine` only, and it must refuse to start when a database connection string, queue or Kafka setting is present). Settings are `MachineGatewaySettings {bind, port, certificatePath, privateKeyPath, heartbeatSeconds, maxSessions}` under `SHIKIGAMI_MACHINE_GATEWAY` and `MachineDaemonSettings {stateDirectory, policyPath, gateway :: GatewayEndpoint {host, port, pinnedFingerprint}}` under `SHIKIGAMI_MACHINE`, declared once in `shikigami-core/src/Shikigami/App/Config.hs` and loaded through Settei like `workspaces`. Both executables live in `shikigami-workers` (`app/machine-gateway/Main.hs`, `app/machine/Main.hs`), are registered in `shikigami-workers.cabal`, in `docs/architecture/packages.md`'s executable table and in `nix/qualification-package.nix`'s `prototypeExecutables`. EP-1 adds `Machine` to `domainRoots` in `tools/style/module-ownership.json` with a rationale comment citing ADR 0075.

**Local policy and admission — EP-2 owns; EP-3 and EP-5 consume.** `shikigami-core/src/Shikigami/Machine/Policy.hs` defines the pure `LocalPolicy` (machine name, `[LocalRepository]` each with identity, local Git object store locator, allowed bases or `AnyApprovedBase`, read and write prefixes; `[AllowedPrincipal]`; `Set OperationClass`; `ContainmentDeclaration` of `SystemdProcessPolicy !ProcessPolicy !IdentityRange` or `NoProcessTools`; `Ceilings {concurrentCommands, processSeconds, outputBytes, diskBytes}`; and `workingTree :: WorkingTreeAccess` whose only constructor is `WorkingTreeRefused`), its strict JSON decoder and validator modelled on `Workspace.Settings`, `policyRevision :: LocalPolicy -> PolicyRevision` as a versioned digest, and the total pure `admitCommand :: LocalPolicy -> MachineId -> FenceView -> CommandEnvelope -> Either MachineRefusal AdmittedCommand` that implements the intersection rule: the machine must equal the daemon's identity, the repository must be hosted, the principal must be allowed, the operation class must be allowed, a process operation requires `SystemdProcessPolicy` and a rule the policy names, the epoch must exceed every fence applied for that workspace, and ceilings must hold. `AdmittedCommand` is a sealed value with a public read view ([ADR 0081](../adr/0081-validated-results-use-private-seals-and-public-read-views.md)); EP-3 executes only `AdmittedCommand`, never a raw envelope. `shikigami-workers/src/Shikigami/Machine/Ledger.hs` retains, under the daemon state directory with fsync and atomic rename: the identity (private key, machine id, gateway pin), applied fences per `WorkspaceRef`, and per `MachineCommandId` the admitted envelope, the receipt and the acknowledgement marker; `recoverLedger` rebuilds the in-memory view on start and refuses to start on a corrupt record rather than treating it as absence.

**Physical workspace interface — EP-3 owns; the existing supervisor keeps consuming.** `shikigami-workers/src/Shikigami/Workspace/Physical.hs` exposes the IO steps already implemented in `ContainedFile`, `GitObjects`, `GitCapture`, `Systemd`, `Collector`, `Provision` and `Allocation` as functions over explicit inputs (binding, admission or profile, record) returning receipts, with no `AppEnv`, pool or transaction argument. `Shikigami.Workspace.Supervisor`, `FileProvider`, `GitProvider` and `Integration` are refactored to call `Physical` for their IO while keeping their PostgreSQL stores; their existing worker-suite cases and the plan 96 native matrix must pass unchanged. `shikigami-workers/src/Shikigami/Machine/Host.hs` executes an `AdmittedCommand` through `Physical`, enforces the envelope deadline locally through the existing absolute-deadline guard and `RuntimeMaxSec`, cancels whole cgroups on `CancelProcess`, writes the receipt into the ledger before sending it, and resends unacknowledged receipts on every new session. Provisioning reads only the Git object store named by the local policy at the approved base; it never reads the working tree.

**Placement, binding and admission snapshot — EP-4 owns; EP-5 reads.** `Shikigami.Workspace.Settings.WorkspaceGrant` gains `placement :: Placement` (closed: `LocalHost | OnMachine !MachineName`; omitted decodes to `LocalHost`), `WorkspaceRepository.source` becomes the closed `RepositorySource` (`HostPath !(WorkspaceLocator "repository-source")`, encoded as the existing string, or `OnMachines !(NonEmpty MachineName)`), `WorkspaceBinding` gains `placement :: Placement`, and `WorkspaceAdmission` carries the placement into the protected snapshot additively per [ADR 0011](../adr/0011-defaulted-agent-fields-preserve-journal-codec-compatibility.md). Binding JSON and digests change for new bindings only, which [ADR 0027](../adr/0027-the-first-release-establishes-one-clean-durable-baseline.md) permits before v1; old bindings decode as `LocalHost` with a `HostPath` source. Selection at admission resolves the grant's placement, requires the machine to be `Enrolled`, requires its containment profile to be `SystemdCgroupV2` before any process adapter is installed for that assignment, and refuses otherwise. `Shikigami.Workspace.ConfiguredHost` selects, per placement, either the existing local adapters or the remote adapters from `shikigami-workers/src/Shikigami/Workspace/RemoteProvider.hs`.

**Durable relay and settlement — EP-4 owns; EP-5 reads.** A remote `DurableAdapter` reserves centrally exactly as its local counterpart does, enqueues one `CommandEnvelope` keyed by `(operationId, attemptId)` so a redelivered dispatch converges on the same command, waits up to the configured `waitSeconds` for a receipt, and on timeout throws so the executor keeps the uncertain-effect reservation and the local finalizer releases the capacity permit ([ADR 0109](../adr/0109-runtime-capacity-admission-shares-accepted-attempt-fences.md)); root usage stays held. The gateway's delivery loop sends `Queued` commands to a connected machine, marks them `Delivered`, and on `Receipt` records the receipt through the owning store (`recordWorkspaceReceiptTx`, `recordProcessReceiptTx`, `GitStore`, `TransferStore`) and the execution owner (`recordIndependentToolReceipt` through the same checks `publishProcessReceipt` performs today), then sends `Ack`. The remote integration adapter sends `Integrate` only when the integration workspace and every worker binding it names share one `OnMachine` placement and refuses otherwise before reserving anything. Command states are the closed `Queued | Delivered | Settled | Refused | Unresolved | Superseded`; `Refused` carries the machine's `MachineRefusal`; nothing moves a command to a failed state on time alone. A disconnected machine leaves commands `Queued` and executions `Unresolved` with pending receipts. A `Revoked` machine refuses new enqueues and retries while retained `Unresolved` commands stay inspectable.

**Partition transfer — EP-4 owns; EP-2 and EP-3 apply the fence.** `TransferIntent` processing checks the workspace's placement. For a connected machine the fence is `FenceOwner` over the session, and the outcome follows [ADR 0063](../adr/0063-handoffs-establish-epochs-only-after-fences-and-versioned-owner-receipts.md) unchanged. For a disconnected machine the operator or coordinator must supply an explicit approved base; the successor is allocated a new `WorkspaceBinding` on its own placement, the old binding is frozen centrally through `freezeWorkspaceTx`, a `shikigami.machine_fences` row records the pending fence, and queued commands under the old epoch are `Superseded`. On the old machine's next session the `Welcome` frame carries every pending fence; the daemon writes each to its ledger and answers `FenceApplied` before the gateway delivers or accepts anything else. Late receipts from the old epoch settle only the former attempt's accounting ([ADR 0060](../adr/0060-safe-recovery-spends-new-attempts-and-retains-independent-receipts.md)) and cannot complete the assignment, because the assignment's current binding and epoch differ.

**Operator surface and metrics — EP-1 owns the enrollment verbs; EP-5 owns inspection and metrics.** `shikigami-server/src/Shikigami/Server/Command/Machines.hs` wraps `Shikigami.Machine.Store` per [ADR 0021](../adr/0021-operator-verbs-wrap-the-owning-library.md); the server does not depend on the workers package ([ADR 0066](../adr/0066-worker-commands-require-retained-scopes-and-fresh-exact-authority.md)). EP-1 creates the module with `shikigami machines offer|approve|revoke --json`, adds it to `compositionModules`, and gives the daemon `shikigami-machine enroll|run`. EP-5 adds `shikigami machines list|inspect --json`, the daemon's `shikigami-machine status|check-policy --json`, and the new `ShikigamiMetrics` instruments `shikigami.machine.sessions` (gauge), `shikigami.machine.commands`, `shikigami.machine.receipts` and `shikigami.machine.refusals` (counters with `outcome`, `operation.class` and `refusal.kind` attributes), and `shikigami.machine.disconnected.age` (gauge with `machine.name`); no identifier or path is an attribute. Neither health probe changes ([ADR 0020](../adr/0020-readiness-covers-only-what-restarting-can-fix.md)).

**Shared process and schema wiring — each child owns its additions.** `Shikigami.App.Config` and its loader, `Shikigami.App.Config.Role`, `Shikigami.Workers.Command` role list, `shikigami-workers.cabal`, `shikigami-core.cabal`, `tools/style/module-ownership.json`, `docs/architecture/packages.md`, `nix/qualification-package.nix` and the migration manifest are shared. EP-1 adds roles, settings, the registry migration and the `Machine` root; EP-2 adds the policy module and ledger; EP-3 adds `Physical` and `Host`; EP-4 adds the command migration, placement fields and remote adapters; EP-5 adds the command module and metrics. Serialize edits to these files, allocate migration numbers only at implementation time, and rerun `just haskell-conventions`, `just domain-value-types` and `cabal test` for every prior consumer. No child changes a declared workflow body; each child confirms this with `just keiro-gate` and, if a patch ever becomes necessary, follows [workflow versioning](../workflow-versioning.md).

**Acceptance ownership.** IR-20 acceptance 1 (enroll, edit, validate, commit, exact artifacts) is built by EP-1, EP-3 and EP-4 and demonstrated by EP-5. Acceptance 2 (local policy forbids a centrally allowed operation; a forged wider command is refused the same way) belongs to EP-2 and is demonstrated by EP-5. Acceptance 4 (sever during a command; local deadline; unresolved not failed; reconnect settles once) is built by EP-3 and EP-4 and demonstrated by EP-5. Acceptance 5 (transfer during a partition; former machine's writes refused; late results cannot complete) is built by EP-4 with EP-2's fence ledger and demonstrated by EP-5. Acceptance 6 (restart daemon and central worker at each side of an accepted operation) is built by EP-3 and EP-4 and demonstrated by EP-5. ## Decision Log

- Decision: The daemon is a physical executor with no durable bookkeeping and no central credential; the central runtime keeps every reservation, epoch, receipt row and attempt in PostgreSQL and receives receipts through the existing independent late-receipt path.
  Rationale: IR-20 requires that a compromised runtime reach no further than each machine's grant and that the daemon hold no provider credentials. The current supervisor opens the central database, so moving it as-is would hand every machine a central credential. The physical steps are already separate modules, and `publishProcessReceipt` already settles supervisor receipts through `recordIndependentToolReceipt`, so the thin daemon reuses ADR 0060 instead of creating a second owner of epochs and receipts.
  Date: 2026-11-04

- Decision: Machine identity is a machine-held Ed25519 key authenticated per session by challenge-response over a TLS connection whose gateway certificate is pinned at enrollment; the gateway is a WebSocket endpoint served through Warp in a new `shikigami-machine-gateway` role.
  Rationale: The private key never leaves the machine, each session is bound to a fresh nonce, and revocation is a registry check at hello. Mori registers `crypton`, `warp-tls`, `wai-websockets` and `websockets` and no X.509 client-certificate helper; WebSocket through Warp shares the health, proxy and load-balancer behavior the server already has. Versions and bounds are verified against Hackage and upstream tags at implementation time.
  Date: 2026-11-04

- Decision: Local policy is the enforcement point. The effective permission is the intersection of central grant and local policy, computed by a total pure function on the machine, and every command is bound to machine, workspace, assignment, epoch, operation, attempt and claim generation.
  Rationale: The request names the machine as the enforcement point and requires a captured or forged command to fail on another machine or under another owner. A pure admission function over a validated policy file and a fence ledger is property-checkable with no runtime, and reusing `ClaimOwner` and `StateRevision "execution-attempt"` keeps ADR 0085's fences intact across the network.
  Date: 2026-11-04

- Decision: Absence is a durable queued state, a timeout is never a failure, and a transfer away from an unreachable machine starts the successor in a new workspace on an explicit approved base while the old machine receives a pending fence before any other exchange on reconnection.
  Rationale: ADR 0063 forbids a successor writing the same resource before the former writer is fenced and settled; a partition makes that proof unobtainable. A new workspace on an explicit base is a different resource, so the successor needs no fence proof from the absent machine, and the old machine's late results settle only the former attempt's accounting under ADR 0060. The request requires exactly this ("Moving one uses fenced handoff and an explicit base").
  Date: 2026-11-04

- Decision: Each platform declares its containment profile; a machine without a qualified profile hosts provisioning, edits and Git operations but refuses process operations at both the central selection and the machine's admission.
  Rationale: The request forbids silent fallback to weaker isolation and excludes native macOS containment from this delivery. Git commits use the trusted Git helper with controlled arguments against a private object store, not repository-controlled code, so they remain available without a process profile.
  Date: 2026-11-04

- Decision: Exact-artifact integration is a machine operation only when every worker workspace and the integration workspace share one machine; integrating commits that live on different machines is excluded from this delivery.
  Rationale: The outbound content contract sends commit identities and changed paths centrally, never Git objects, so neither the central host nor another machine holds the objects an integration needs. Artifact transport between machines is a separate design with its own trust questions and is recorded as future work rather than smuggled in through receipts.
  Date: 2026-11-04

- Decision: The daemon binary `shikigami-machine` lives in `shikigami-workers` for the first delivery, starts with no database, queue or Kafka configuration, and a dedicated lightweight package is a deliberate exclusion.
  Rationale: The physical workspace modules live in `shikigami-workers`, the Nix cohort asserts seven application packages, and ADR 0003 makes a package split a recorded decision rather than a drift. Splitting the physical modules out is real work with no acceptance value for IR-20; the weight cost is recorded so a later plan can take it deliberately.
  Date: 2026-11-04

- Decision: Create the intention with `mina ci --json` and associate this MasterPlan and all children with `intention_01m6m0b6zxebfv3yatcy7fvbgk`.
  Rationale: Requested by the user at creation; no recurring automation is implied.
  Date: 2026-11-04
