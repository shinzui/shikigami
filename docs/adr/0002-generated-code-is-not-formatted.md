# 0002. Generated keiro-dsl output is excluded from the formatter

Date: 2026-08-19

Status: accepted


## Context

This repository formats every file on commit: `treefmt` runs fourmolu over
Haskell and cabal-fmt over Cabal files, wired through git-hooks so a commit that
would change formatting fails.

`keiro-dsl scaffold` writes Haskell and Cabal files carrying the banner
`-- @generated by keiro-dsl ...; do not edit.` and overwrites them on every run.
The two arrangements collide, and the collision is not cosmetic. Running the
formatter after the first scaffold rewrote four of five generated modules and
the generated conformance `.cabal`:

```text
$ nix fmt -- --fail-on-change --no-cache
ERRO file has changed path=.../Shikigami/AgentRun/Generated/WorkflowFacts.hs
ERRO file has changed path=.../Shikigami/DanwaConversation/Generated/WorkflowFacts.hs
ERRO file has changed path=.../keiro-dsl-conformance.workspace.shikigami/src/Main.hs
formatted 12 files (5 changed)
```

Two properties break at once. The generated-code firewall says a `-- @generated`
file is never hand-modified, and a formatter is a hand. And determinism — that
scaffolding an unchanged specification twice reports every module `unchanged` —
is what makes a committed generated file trustworthy: it is evidence that the
file is what the current specification produces. Once the committed bytes are
formatter output, the next scaffold reports `overwritten`, and the bytes
alternate between generator output and formatter output indefinitely.


## Decision

**Exclude generated keiro-dsl output from `treefmt`, and only generated output.**
The excludes live in `flake.module.nix`:

```nix
treefmt.settings.global.excludes = [
  "shikigami-core/src/Shikigami/Generated/*.hs"
  "shikigami-core/src/Shikigami/*/Generated/*.hs"
  "shikigami-core/src/keiro-dsl-conformance.workspace.*/*.cabal"
  "shikigami-core/src/keiro-dsl-conformance.workspace.*/src/Main.hs"
];
```

`flake.module.nix` rather than `nix/treefmt.nix` because the latter is
seihou-managed and would lose the change on a template upgrade.

The create-once `KeiroConformance.Expectations` module inside the generated
conformance package is deliberately **not** excluded. keiro-dsl never overwrites
it; it is application-owned code that a human edits to accept a conformance
change, and it is formatted like any other module.


## Alternatives rejected

**Let the formatter win and drop the determinism check.** This removes the one
mechanical guarantee that a generated file on disk is what the current
specification produces. Without it, a hand edit to a generated module is
indistinguishable from a formatter pass, and reviewing a generated diff becomes
guesswork.

**Format, then commit, and accept churn.** The churn is not bounded: every
scaffold produces a diff and every format produces the inverse diff, so every
change to the specification arrives mixed with unrelated reformatting of files
nobody wrote.

**Ask keiro-dsl to emit formatter-stable output.** Reasonable upstream, and
worth raising, but it makes this repository's formatter configuration a
constraint on a shared toolchain used by services with different formatter
settings. The exclusion is local and correct regardless of what upstream does.


## Consequences

Generated modules are not fourmolu-formatted and will look slightly different
from hand-written ones. That is the intended signal: they are not hand-written.

A new generated artifact in a location the globs do not match will be formatted
silently, and the next scaffold will report it `overwritten`. The globs are
therefore part of the adoption surface — extending the specification to a node
kind that emits into a new directory means extending them in the same change.
`Shikigami.KeiroSpecificationSpec` catches the adjacent failure (a generated
module missing from `shikigami-core.cabal`), and
`just keiro-scaffold` catches this one, because it regenerates and then runs
`git diff --exit-code`.
