1. The delivery loop

Adaptation is a bounded runtime decision. A compiled Flow reads current state, asks for a typed proposal, validates it, and executes admitted operations. Workers run through the durable Skill harness. The same command implementation serves Flow and model-tool coordination.

What changed in the runtime

Accepted model/tool turns now survive restart, assignment models stay pinned, governed workspaces enforce real process fences, and admitted capacity supports useful overlap. The remaining finite-delivery gate is the actual-model trial; recurring mandates have their own child plan.

Why seven separate children?

Resource conservation can be proven before a coordinator runs. Turn persistence and policy state need one atomic boundary. Session continuity, recurrence, and integrated qualification each need their own evidence and authority.

4. What must survive a restart

The design separates identities with different lifetimes. Durable state and explicit receipts preserve facts when workflows resume, workers change, or an external result is uncertain.

Admission before dispatch

Validate current authority, target availability, graph shape, ownership, models, cutoff, and limits. Commit the accepted decision and stable operations before any dispatch. New revocation can stop pending work while preserving the historical decision.

Compatibility is part of delivery

Existing fixed supervisors and old journals retain their behavior. Workflow-body changes use declared patches, compatible codecs, generation rotation, and just keiro-gate under the workflow versioning rules.

5. A finite delivery walkthrough

This walkthrough follows the delivered contracts. The native fixture exercises exact repository integration and recovery with deterministic providers; the actual-model coding trial remains open.

Admit the outcome

A user asks for a repository change and specifies the user journey, allowed edits and checks, model preferences, shared budget, and cutoff. Store the authoritative checkpoint and one root.

Start useful work

The coordinator reads instructions and current owners. It can work alone for a small task or admit two independent assignments in isolated workspaces with pinned settings.

Adapt on a finding

A worker discovers a shared interface dependency. The coordinator proposes narrower assignments and a follow-up, validates them against the current checkpoint, and records the accepted change.

Recover mid-operation

A restart occurs after a tool may have changed a file but before its result was recorded. Resume the same logical operation, reconcile the effect, and preserve accepted turns and held usage.

Transfer safely if needed

Reconcile pending effects and advance ownership with workspace fencing. A former owner’s late write is refused; unknown effects block conflicting successor writes.

Check the combined result

Integrate exact worker artifacts in a separate workspace. Run actual repository checks and the requested user journey, then submit versioned evidence for checkpoint-owner acceptance.

Honest stopping: if a required workspace, authority, or check remains unavailable, retain the useful artifacts and name the precise unresolved scope. Finite success closes only after integrated acceptance. Publication, merge, and deployment require their admitted authority.

6. What proves completion

Worker-local green checks do not establish the combined result. IntegratedAcceptance binds the objective and criteria revision to exact combined artifacts, actual checks, user-journey evidence, and unresolved limitations.

Mechanics and fault evidence

  • Last-slot races conserve root resources.
  • Restart and message redelivery reuse accepted work.
  • Former owners are fenced after handoff.
  • Forbidden proposals, models, and actions fail before dispatch.
  • Useful overlap and fair progress are measured across runtime processes.

Full delivery evidence

  • An early finding produces a validated adaptation.
  • Exact combined source passes repository checks and the user journey.
  • Real journals, providers, workspaces, and recovery are exercised.
  • A bounded live model/coding trial supports the claim.
  • Resource use, latency, rework, uncertainty, and limitations are retained.

7. Continuity does not imply recurrence

Continuing session · EP-4

Retain a worker’s useful context

A session can remain idle and later receive a follow-up assignment. Its stable identity, accepted results, and ownership survive. This continuity grants no permission to schedule future work.

Ongoing mandate · EP-7

Admit repeated bounded cycles

The user explicitly admits cadence, resource envelope, expiry, and stop controls. Each wake reads current authority and checkpoints, then reuses the coordinator and execution root.

  1. Wake: worker events are hints; the existing timer dispatcher provides scheduled recovery.
  2. Reconcile: coalesce overlap, read current instructions, and process bounded new evidence from the watermark.
  3. Checkpoint: record accepted cycle progress and the desired next wake together; repair wake registration after crashes.
  4. Continue or stop: successful ongoing cycles can continue. Cancellation or expiry blocks new admission and preserves unresolved in-flight effects. Old timers cannot revive a stopped mandate.

8. Observation and proposal admission

Independent watchdog · delivered

watchdog-sweep reads bounded metadata, classifies quiet work and assesses drift under its own allowance. Findings are advisory; it cannot cancel, transfer or complete the observed objective. Independent ledger inspection and telemetry expose missed cadence. See watchdog notices and eight-case qualification.

Unrequested work · delivered

propose-work observes permitted activity and asks a person to accept a bounded proposal. Human acceptance creates an objective; only an explicit standing policy can also fund and dispatch an admitted coordinator. See the proposal guide and operator setup.
