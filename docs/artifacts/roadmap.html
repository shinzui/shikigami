The product contract

Shikigami runs a declared behavior when a trigger fires, but that simple sentence carries a strong architectural promise: the run is durably identifiable, replay-safe, attributable to a principal, authorized at the point of external action, observable through evidence and status, and operable both as a Kikan service and as a lightweight one-off runner.

Replay is a product property

Workflow code records deterministic decisions. World-facing behavior crosses journaled capability boundaries, and any workflow-body shape change is guarded by an explicit Keiro patch.

Authority is checked at action time

Recorded Meibo identity keys durable state, but identity alone is not permission. Protected tools and sinks require fresh exact authorization immediately before the external action.

Delivery truth has one owner

The journal owns enqueue intent; outbox receipts own retries, rejection, and downstream delivery. Semantic coalescing never becomes a second delivery-state machine.

What exists today

Durable foundations are implemented, while the new decision and adaptive-worker layers remain planned. Recorded source checks, installed binaries, live service qualification and production readiness each have separate evidence.

The practice-review safety sequence

The P0/P1 wave is one architecture chain. Each link owns a different fact; skipping or duplicating a link creates the defects identified by REV-1, REV-2, REV-4, and REV-7.

1 · Admission

Authenticate and bind the resolver

Decode a versioned resolution envelope, authenticate a human or approved artifact, and require the verified subject to match the claimed resolver.

2 · Entitlement

Prove this subject may resolve

Check the exact review/practice boundary. Authentication establishes who acted; entitlement establishes whether that action is allowed.

3 · Durable decision

Journal a replay-safe receipt

Store bounded authority coordinates—not tokens or raw evidence—and replay without repeating the external security operation.

4 · Semantic reservation

Coalesce equivalent attention

Reserve the normalized dispute, link each review, and create the winning outbox message in the same transaction.

5 · Delivery

Let receipts own transport truth

Publish the same deterministic message identity. Transient failure retries; permanent refusal is terminal; neither creates a second semantic signal.

6 · Evidence

Prove the claimed matrix

Conformance fixtures and operator docs must cover authorization, replay, coalescing, recovery, and the production profile path before plan 46 closes.

Current breakpoints: the JournalAlreadyPresent attention branch can commit without condemning the transaction, and resolution verifies identity without proving resolver entitlement. Plan 60 owns the former; plan 61 owns the latter.

Typed decisions inside durable Flows

IR-12 expands beyond the existing router’s one journaled decision. A compiled Flow will invoke a registered typed program at a named step, choose an admitted model, validate the result, and branch through governed capabilities.

Prepare a contract before dispatch

The planned registry binds program implementation and schema versions, input digest, validator, exact model tuple, policy and credential reference. Payload data may select only among admitted aliases. Unknown programs, changed bindings and unauthorized choices fail before a provider call.

Distinguish replay from a new attempt

A completed decision replays its journaled result without another call. A crash after a provider acts but before the journal append may require another attempt: the evidence ledger retains both attempts and uncertainty. This is not an exactly-once provider guarantee.

Adaptive autonomous delivery: the planned chain

UC-1 is a draft use case for verified outcomes through a recoverable coordinator. MasterPlan 14 selects a compiled adaptive Flow for coordination and a durable Skill harness for workers. It preserves existing fixed supervisors.

Adaptation remains a validated proposal

A model can propose splitting work, narrowing an assignment, requesting a specialist or changing concurrency. Plan 85 checks current objective state, owners, allowed model settings, capabilities and root limits before accepting commands. A proposal cannot create new authority or reset its allowance.

Mechanics and full integration have different gates

Early store, transcript and session tests can use fixtures. Full worker handoff needs a real fenced workspace from IR-11 and authoritative checkpoint integration from IR-13. Plan 86 additionally proves useful overlap, exact combined-source validation and a bounded live coding trial. Neither prerequisite request has a selected full implementation plan.

One owner for each recovery and completion fact

The new initiative coordinates several durable records without making them competing histories. Stable references connect them; atomic transactions or idempotent intent/receipt protocols keep accepted progress aligned.

Accepted work survives a handoff

A session’s stable worker identity is separate from assignment id, child run id and owner epoch. A successor reads accepted artifacts and reconciles pending effects before gaining write authority. Lease expiry is insufficient evidence that an old process stopped.

Completion binds to the integrated result

Acceptance records the objective and criteria revision, exact combined repository artifact, real command results and user-journey evidence. A green result from an obsolete worker branch does not qualify a newer combined tree. Unresolved conflicts and uncertain effects remain visible.

Finite delivery and recurrence have separate authority

Continuing worker sessions support follow-ups without creating permission to schedule future work. Recurrence adds a distinct admitted mandate over the same coordinator and resource root.

Each recurring wake rereads authoritative checkpoints, instructions, ownership and pending work. Events and timers are hints, coalesced into one eligible cycle. Cancellation, revocation, expiry and absolute cutoff deny new admission while allowing accepted outcomes and uncertain effects to be recorded and reconciled.

Qualify the actual workload before promotion

Plans 79 and 80 record October source and installed-role checks, but the local service workload remains blocked and production remains unproven. Packaging is now partially delivered in plan 31; a full operable stack is still open.

Start the named local workload with PostgreSQL 18, Shomei and Kikan-En, then a real response provider and Kawa; Danwa and Kizashi support durable human waits. Kafka and Kubernetes are not prerequisites for that workload. plan 77 separately proposes bounded read-only Kubernetes observations; plan 78 separately proposes submit/observe external jobs and is not selected as MasterPlan 14’s executor.

Execution surfaces are distinct. Plan 80’s HTTP responses and foreground launches have recorded evidence. Background Codex/Claude CLI responses remain blocked by Baikai BUG-1 in the selected release. Foreground process success does not prove a restartable worker transcript, a delivered sink, or production readiness.
