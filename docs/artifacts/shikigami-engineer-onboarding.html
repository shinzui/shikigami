Architecture field guide · implementation + planned portfolio

How Shikigami fits together

Shikigami is Kikan’s declared-agent runtime. A typed Dhall declaration says who an agent is, when it runs, what behavior it invokes, and which outputs it may request. Durable workflows and storage turn those requests into recoverable work. Typed Flow decisions and the authenticated agent/run HTTP API are implemented. Model/tool-turn recovery is implemented; continuing-worker mechanics are partial. Real workspace/checkpoint providers and adaptive coordination remain gated below.

Dhall declarationsHaskell FlowKeiro workflowsPostgres + PGMQKafka activity.v1Kioku memory
Start here: a declaration is intent, not authority. The runtime still resolves a principal, checks grants and exact-action authorization, journals durable steps, and records delivery separately.

1. Two execution paths

The deployed Kikan service and the one-off CLI share shikigami-core, but have different boundaries and operational needs.

Declaration

behavior can name a registered Shikumi/Handan program, a Baikai skill, or a compiled Flow. trigger chooses schedule, stream, or addressed event. sinks, identity, and memory policy complete the contract. The current runner rejects the schema’s Deterministic arm.

Durability

Keiro journals agent runs, approval children, and Danwa conversations. Flow steps use replay-safe capabilities for waits, memory, routing, typed decisions, and sink intents. Changing a workflow body requires the workflow versioning procedure.

2. Event streams, inbox, queues, and outbox

activity.v1 is the shared activity stream. A second public integration-event topic carries addressed events, including Danwa messages when enabled. Schedule timers, a direct enqueue-run command, and authenticated HTTP run requests can produce run jobs without Kafka.

Run queue

The generated RunJobMessage envelope has one explicit route and a versioned codec. Producers include HTTP acceptance, the CLI, scheduler, Kafka inbox, delegation, and conversation routing. The supervised worker drains shikigami_run_jobs; its retry policy has shikigami_run_jobs_dlq.

Feedback loop

A permitted Kawa digest may reappear as an activity.v1 envelope and trigger another agent. The local stub-kawa can demonstrate this path; real service ownership remains with Kawa. Danwa events arrive through its public topic, and replies use its HTTP API.

3. Tables, projections, and read models

“In Postgres” does not imply one owner or one replay rule. Identify the authority for each fact before editing storage or writing an operator query.

Read-model rule: a replayable event stream, an inline SQL projection, a Kioku read model, and a transport queue have different recovery semantics. The RunEvidence SQL targets use preserve-and-reconcile; lifecycle events alone cannot restore their rich payload.

4. Permission is checked at the action boundary

The runtime distinguishes the identity named in a declaration from the authority to perform a particular action. Protected external I/O fails closed when authorization is disabled or trust material is incomplete.

Identity and grants

Deployed runs use a Meibo principal projection and require an active agent. shikigami grants list|grant|revoke manages the database-backed per-agent, per-sink-kind C11 gate. A declared sink is not automatically granted.

Exact target and proof

Kikan-En evaluates the exact source, recipient, intention, thread, or channel target. Shomei issues the machine token; an En signed decision proof is verified locally. Denial performs no protected I/O; an outage or invalid proof is a distinct authorization failure.

Default behavior: disabled action authorization permits no protected external action, even to stubs. The one-off binaries currently wire a deny-all authorizer, so --workspace does not enable workspace.read and one-off runs do not publish protected sinks.

6. Standalone CLI: first useful run

Work from the repository root inside the Nix shell. HTTP provider and foreground-launch operations now have separate documented surfaces; background CLI responses remain gated in plan 80. The full project currently expects the co-developed Kikan-En contract/client checkout at the sibling paths in cabal.project.

Build and validate

nix develop
cabal build all
cabal run shikigami -- validate agents/heartbeat.dhall
cabal run shikigami -- render-lifecycle agents/detectors/at-risk-customer-flow.dhall

validate parses typed Dhall; render-lifecycle prints Mermaid for a registered Flow agent. Neither needs Postgres or a model key.

Run one behavior without services

cabal run shikigami-run-behavior -- \
  --agent agents/heartbeat.dhall \
  --payload '{"source":"onboarding"}'

Prints behavior output JSON using the stub provider by default. It does not create a session or dispatch sinks. This command supports registered programs and Skills; it rejects Flow, Deterministic, and sanctioned-profile requirements.

Add Postgres for memory

process-compose up             # in another dev-shell terminal
# or, with an existing Postgres: just create-database
cabal run shikigami-agent-run -- --agent heartbeat
cabal run shikigami-agent-run -- --agent heartbeat

agent-run opens a Kioku session, recalls prior memory, runs behavior, records a learning, and completes the session. The second run can recall the first. --from-activity FILE folds an activity envelope into memory without running behavior.

Exercise the deployed queue path

cabal run shikigami-worker -- --agents agents
cabal run shikigami -- enqueue-run heartbeat --payload '{}'
# Optional, with an external broker: run consume-stream for activity.v1

The worker drains the queue. Stream consumption needs a separately running broker; the bundled process-compose.yaml starts Postgres only. Protected sink effects require an active principal, C11 grant, and Kikan action-authorization configuration.

Which binary? shikigami is administrative; shikigami-run-behavior and shikigami-agent-run are the one-off leaf package; shikigami-worker, shikigami-scheduler, shikigami-consume-stream, and shikigami-consume-events are independent long-running roles. Full CLI reference →

9. Recovery records operations; handoffs preserve ownership

The current outer agent workflow can journal a behavior result. That boundary alone cannot restore a Skill’s uncommitted intermediate model/tool history after a crash. Completed plan 83 adds a distinct protected operation transcript, pinned context/policy state and durable submit/observe recovery.

A provider can act before its result is durably accepted. Recovery therefore distinguishes a committed outcome from an uncertain dispatched attempt. Logical retries retain the operation key; actual attempts receive separate ids and consume the shared resource envelope. Unknown usage remains reserved rather than being erased by restart.

Handoff is an effect-safety protocol. Advancing an owner epoch must be enforced by the actual workspace/effect owner. A process lease timing out, a model reporting completion or a coordinator accepting a message cannot fence a still-running writer.

10. Model scope, completion and recurrence

Plan 80 exposes current response configuration and foreground agent launches. The delivered catalog supports model selection for a typed Flow decision. Whole-assignment execution selection is implemented by completed plan 82. They reuse a catalog but have separate permissions and replay bindings.

Completion is evidence about a combined artifact

Plan 86 binds acceptance to the objective/criteria revision, exact combined repository tree, actual checks and user journey. IR-13 owns objective completion; plan 85 supplies validated coordination. Worker-local green checks are input evidence, not the integrated verdict.

Continuity does not enable recurrence

Plan 87 requires an explicit mandate with cadence, authority, expiry and cutoff. Each timer/event wake rereads current checkpoints and coalesces work. Finite delivery can qualify before this phase; new recurring cycles retain the resource root and stop admitting work after revocation or expiry.

Use the readiness report to choose a live workload and see its remaining service gates. Source checks and installed packages are useful evidence, but they do not establish delivery, human-wait recovery or production promotion.

11. Public agents and durable run resources

MasterPlan 15 is complete. The agents mount uses configured bearer authentication; health probes remain public. Discovery reads boot-time declarations and the current lifecycle directory. HTTP requests address an admitted agent directly, independently of its normal trigger.

shikigami-client agents list|show discovers agents; runs request|show|list|wait handles work. The HTTP API guide covers configuration, pagination, payload bounds, wait exit codes and pre-workflow DLQ retention. No per-caller agent permissions, HTTP cancellation, or signed-attestation endpoint is added.
